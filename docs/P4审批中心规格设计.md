# P4 审批中心 · 规格设计（真实审批引擎接入 + P3c 延后 3 项 + D15）

> **产出**：产品经理 许清楚｜**依据**：PRD v1.1 §6.16（L1054–1070）、L89/L110/L211/L224/L1005/L1478/L1510、延期台账 D5/D13/D14/D15/D17、P2/P3 既有规格（R3/R6 修订口径）、approval 域现状代码（commit `56badd8` 实证）
> **范围**：① 真实审批引擎（替换 `LocalApprovalGateway` 即审即过）② 统一审批工作台 UI（替换前端 `/approval` 占位页）③ P3c 延后 3 项（合同类型字典+补充签订、超收/计重、最低价同步开关）④ D15 合同供货范围校验
> **铁律（不可妥协）**：**只换实现，不改契约**——业务代码只经 `ApprovalGateway` 接口调用；`ApprovalTaskSpec`/`ApprovalDecision`/`ApprovalCallbackHandler` 接口签名、`ApprovalStatus` 状态机、7+1 类 bizType 枚举、回调幂等语义（仅 CREATED/IN_PROGRESS 可流转、终态重复回调忽略、重提=新任务）**一律不得破坏性变更**。P4 换掉的是 Local 实现的"引擎内部"，不是接缝。
> **架构前提（硬约束）**：节点/审批人角色/金额阈值**全部配置化**（表驱动，见 §3.1）——业务拍板（拍板清单 7 项）后**只改配置数据，不改代码**。这是"节点未定不阻塞开工"的前提，写入本规格硬约束。

## 2. 现状基线（代码实证，commit `56badd8`）

### 2.1 接缝与实现

| 组件 | 现状 | P4 处置 |
|---|---|---|
| `ApprovalGateway`（create/callback） | 接口契约，业务代码唯一入口 | **不动** |
| `ApprovalTaskSpec`（bizType/bizId/title/applicant/payloadJson） | 发起规格 | **不动**（字段够用；applicant 现未落 task，见 §2.3 缺口④） |
| `ApprovalDecision`（APPROVED/REJECTED） | 结论枚举 | **不动** |
| `ApprovalCallbackHandler`（bizType/onApproved/onRejected） | 8 个业务处理器 | **不动**（回调事务语义保持） |
| `LocalApprovalGateway`（@Primary） | 即审即过：create 落 task；callback 幂等流转+分发 handler；PURCHASE_APPLY 通过时 currentNode 直推第二节点 | **替换**为 `WorkflowApprovalGateway`（真实引擎）；Local 保留为测试桩（@Profile/test） |

### 2.3 现状缺口（P4 要补的清单）

1. **无审批人解析**：task 无候选人，任何登录用户都能 approve（`hasAnyPerm` 粗粒度）——违背 PRD L1070"审批中心只展示当前用户有权处理的单据；前端隐藏不能代替后端校验"。
2. **节点不流转**：仅 PURCHASE_APPLY 桩推进 currentNode，无逐节点待办；`approval_node`/`approval_record` 两表存在但**基本未写入**。
3. **无通知**：审批完成后无任何通知（PRD L110"审批完成后通知申请人或业务对方"）。
4. **task 无 applicant 落库**：`ApprovalTaskSpec.applicant` 未写入 `approval_task`（实体无该字段），待办"按申请人视角+通知申请人"缺数据基础。
5. **无审计明细**：approval_record 未记录操作人/时间/动作，BR-19（L1094"审批…必须留痕"）仅靠 task.remark 兜底，不达标。
6. **前端空壳**：菜单"审批中心"（id 10，path `/approval`）→ `frontend/src/router/index.js:56` 指向 `ModulePlaceholder.vue`，views 下无 approval 页面（台账 D5 三层区分之②）。
7. **阈值散落占位**：合同 50 万（`@Value` 默认值，yml 未显式写）、D14 50 万（yml 显式注释"待业务拍板"）——均无业务拍板依据。

## 3. R1 真实审批引擎

### 3.1 表驱动节点设计（★硬约束）

**原始需求复述**：PRD L1005"审批流：固定流程基线；**生产版本可配置审批角色和条件**"；§6.16 L1069"生产版本需要支持审批人、节点……"。

**规格要求（硬约束，写进 Design 评审门槛）**：

- 新建配置两表（DDL 级）：
  - `approval_flow_def(id, flow_key UNIQUE, biz_type, flow_name, enabled, remark, BaseEntity)` —— 每类 bizType 一条流（DAILY_AUTH 同机制）；
  - `approval_node_def(id, flow_key, node_code, node_name, seq, approver_type, approver_value, amount_min NULL, amount_max NULL, sign_type, BaseEntity)` —— 节点序、审批人解析规则、金额生效区间、会签/或签。
- `approver_type` 取值与解析：
  - `ROLE`：approver_value=系统角色编码（如 `dept_head`/`purchase_dept`/`finance`/`procurement_lead`），解析出该角色全部在职用户；
  - `DEPT_HEAD_OF_APPLICANT`：申请单据部门的部门负责人（数据范围=本部门，对齐 PRD §2.1 L157）；
  - `USER`：指定具体用户（兜底，慎用）。
- `sign_type`：`ANY`（或签，任一人审批即过，**默认**）/ `ALL`（会签，需业务拍板才启用）。
- 金额阈值即节点属性（`amount_min/max`）：CONTRACT 升级、DAILY_AUTH 超限等**全部收编进节点配置**，不再散落 yml（`app.order.daily-auth-limit` 保留为 D14 业务参数读取源，P4 由引擎按 payloadJson.amount 落到节点匹配，两处取值口径对齐，Q6 跟踪）。
- **业务拍板后只改配置数据**：拍板清单 7 项结论 → `approval_flow_def/approval_node_def` 的 UPDATE/INSERT + 既有在途任务不受影响（新任务按新配置）。禁止把节点写死在 Java 代码。
- 种子数据 = §2.2 现占位口径（两级申请链、合同 50 万升级、D14 50 万），保证未拍板也能按默认上线。
- `LocalApprovalGateway` 的两级推进语义（DEPT_HEAD→PURCHASE_DEPT）迁移为引擎按 `approval_node_def.seq` 通用流转，特判删除。

**AC**：
1. 种子配置下，PURCHASE_APPLY 任务创建后 currentNode=第一节点，待办仅出现在该节点候选审批人的列表中；
2. CONTRACT 金额 60 万（>50 万）→ 两节点流转；30 万 → 单节点；
3. 修改 `approval_node_def` 审批人角色（不改代码不重启）→ 新建任务按新配置解析；
4. 业务回调（approve/reject）接口签名与回调幂等行为与 P3 回归完全一致（`ApprovalGateway` 契约测试全绿）。

**与现状差异**：即审即过 → 逐节点待办流转；特判节点链 → 通用配置驱动；yml/@Value 阈值 → 节点行属性。
**改动面预估**：后端新增引擎服务（流程解析/候选人计算/节点推进）+ 2 DDL + 种子数据；`LocalApprovalGateway` 替换为新实现（接口不变）；`ApprovalTaskServiceImpl` 扩展；预估后端 3–5 天，含契约回归。

### 3.2 审批人解析与权限收紧

**原始需求复述**：PRD L1070"审批中心**只展示当前用户有权处理的单据**；前端隐藏操作不能代替后端权限校验"；§2.3 角色权限矩阵 L184（部门负责人/招采/财务分域审批）、L189（财务预算审批）。

**规格要求**：
- 待办查询按"当前用户 ∈ 当前节点候选人"过滤（服务端强制，非前端筛选）；
- approve/reject 端点增加服务端校验：当前用户必须是该任务当前节点的候选人（非候选人 → 403 语义业务码）；
- 权限键沿用 P1 `module:action` 范式：`approval:todo`（查看待办）、`approval:approve`（审批动作）、`approval:done`（已办）；粗粒度 `hasAnyPerm` 替换为具名权限键；
- 角色编码与 P1 系统角色/员工模型对齐（P5 SSO 接入后仅换用户来源，解析逻辑不动）。

**AC**：①非候选用户调 approve → 拒绝且不留痕；②候选用户列表页只见自己可办的待办；③隐藏菜单/按钮的用户经 API 直调仍被拦截（对齐 L1070）。
**与现状差异**：人人可审 → 按角色+数据范围可审。
**改动面预估**：待办查询改造 + 权限键种子 + 服务端校验；1–2 天。

### 3.3 节点流转 / 待办 / 审批意见

**原始需求复述**：§6.16 L1069（待办、审批意见）；L1062 定标"驳回并返回比价环节"、L1065 结算"驳回并回写付款条件"等由各业务处理器既有回调承载（不动）；采购申请驳回可重提（§8 L1112，既有）。

**规格要求**：
- `approval_node`（既有表）启用：每节点创建时写候选节点行；节点完成时回填 approver/action/comment/status；
- 节点流转：当前节点 ANY 签通过 → 推进 seq+1；全部节点通过 → 任务 APPROVED → 分发既有 `ApprovalCallbackHandler`（同事务语义不变）；
- 任一节点驳回 → 任务终态 REJECTED，直接分发 onRejected（不走后续节点；PRD 各类"驳回并返回 X"语义由业务处理器既有实现承载）；
- 驳回必填意见（Controller 已有校验，保留）；同意意见可选；
- 重提 = 新任务（既有契约），旧任务及节点记录全量留痕。

**AC**：①两级申请：第一节点通过 → 待办出现在第二节点；第二节点通过 → 业务 APPROVED；②第一节点驳回 → 直接 REJECTED，第二节点无待办；③同任务重复回调 → 忽略（幂等回归）；④驳回重提 → 新 taskId，旧任务链完整可查。
**与现状差异**：单次 callback 即终态 → 逐节点多次 callback。
**改动面预估**：引擎核心；与 3.1 合并计。

### 3.4 并发校验（乐观锁 + 状态机防重复审批）

**原始需求复述**：§6.16 L1069"并发校验"；§10.4 L1238 通用字段 `version` 乐观锁。

**规格要求**：
- `approval_task` 加 `version`（BaseEntity 已含则启用）：审批动作 UPDATE 带 `WHERE version=?`，冲突 → 提示"单据已被处理"（3002 语义），防两人同时审批同一任务双推进；
- 任务状态条件更新（仅 CREATED/IN_PROGRESS 可流转）与既有幂等双保险；
- 节点行同机制（version 条件更新）。

**AC**：①两并发请求同一任务 approve → 恰好一成功一冲突提示，任务/业务单据只推进一次；②审批与驳回并发 → 终态唯一。
**与现状差异**：无并发防护 → 乐观锁+状态机双保险。
**改动面预估**：DDL +1 列（若无）+ 条件更新；0.5 天。

### 3.5 审计日志（approval_record 扩展）

**原始需求复述**：§6.16 L1069"审计日志"；BR-19 L1094"审批、驳回……必须留痕"；PRD L1216 `approval_instance`（PRD 数据模型命名，对应现状 approval_task 体系——沿用现状表名，规格注明映射）。

**规格要求**：
- `approval_record`（既有表）启用并扩展：每次审批动作落一行（taskId/nodeId/approver/action(同意/驳回)/comment/approver_name 快照/created_at——操作人与时间由 BaseEntity 承载）；
- task 终态时由引擎写 `operation_log`（BR-19 通道，复用 P1 审计底座）；
- 已办列表 = approval_record 按 approver 查询。

**AC**：①一次两级审批产生 ≥2 条 record，含操作人/动作/意见/时间；②已办列表与 record 一致；③operation_log 有审批终态留痕。
**与现状差异**：record 空转 → 全量留痕。
**改动面预估**：DDL 扩展 + 写入逻辑；0.5 天。

### 3.6 通知（站内即时 + 列表红点）

**原始需求复述**：L110"审批完成后**通知申请人或业务对方**"；§6.16 L1069"通知"；PRD L200 工作台待办（一期默认隐藏，不作验收）。

**规格要求（裁量：一期站内即可，外部渠道 v1.x）**：
- 站内通知最小集：任务创建（通知审批人：您有新待办）、任务终态（通知申请人：申请/结算/合同…已通过/驳回，带意见摘要）；
- 载体：新建 `user_notice` 轻量表 + 顶栏红点数接口（复用前端布局既有消息位即可，不建独立消息中心页）；
- 通知与业务事务解耦（事务提交后发，失败不影响审批主流程）；
- `<!-- D5 -->` 短信/企微/钉钉等外部渠道列 v1.x（PRD L1007 消息模板 / L224），本期仅在通知表预留 `channel` 字段。

**AC**：①审批人登录见红点+待办数；②审批终态后申请人收到站内通知（含结论与意见摘要）；③通知失败不回滚审批事务。
**与现状差异**：零通知 → 站内闭环。
**改动面预估**：DDL + 发送点 + 红点接口；1–1.5 天。

## 4. R2 统一审批工作台 UI（替换 `/approval` 占位页）

## 6. R4 D15 合同供货范围校验

**原始需求复述**：主流程 docx《场景二-流程与节点说明》第 2 条——日常采购"必须选择包含已定标价格清单且处于有效期内的合同……并确认商品在**允许供货范围**内"；《预算、授权与审批控制规则》表第 4 行——"新供应商、新价格或**不在合同及定标价格清单范围内**→重新定标或合同审批，不能直接生成订单"。台账 D15：**无清单合同（框架/存量）可任意 SKU 下单**——A1 免检判据的已知副作用。

**方案选项**：

| 方案 | 口径 | 优点 | 缺点 |
|---|---|---|---|
| **A（建议）** | 供货范围 = 该合同关联定标的 `award_item` SKU 集合；无定标的手填/存量合同 → 首次下单前维护合同 SKU 白名单页签（轻量表，可空=维持 A1 免检兜底额度闸） | 零新概念：award_item 数据现成；白名单仅覆盖真空白；与 docx"合同及定标价格清单范围"原文精确对齐 | 手填合同需一次性维护动作 |
| B | 无清单合同一律不允许下单（强制补录价格清单） | 口径最严 | 与框架协议"仅金额控制"业务定位冲突，存量合同全卡死 |
| C | 不校验（维持现状） | 零成本 | 违背 docx 控制规则表第 4 行，审计不接受 |

**建议：方案 A**（最低风险：默认不改变任何现网可下单行为，仅补"有定标→校验 SKU∈定标范围 / 无定标→白名单兜底"一层；未拍板按 A 落地，Q10 跟踪）。

**规格要求（按 A）**：
- 下单第四重校验扩展：合同**有** contract_price_item → 沿用 A1 硬拦截（sku+价格命中）；合同**无**清单但**有**关联 award → 校验每行 SKU ∈ 该 award 的 award_item SKU 集，未命中 → 4000 拦截（文案"SKU 不在合同供货范围（定标价格清单）内"）；两者皆无 → 白名单表命中校验，白名单为空 → 维持现网行为（额度闸兜底）+ 操作留痕；
- 拦截动作与 docx 对齐：提示"重新定标或合同审批"，不提供旁路。

**AC**：①有清单合同：A1 行为回归零差异；②无清单+有定标：SKU∈定标范围 → 成功；不在 → 4000；③白名单合同：命中 → 成功；④空白名单合同 → 现网行为不变（额度闸）+ 留痕。

**改动面预估**：校验链一个分支 + 白名单表 + 合同页签；后端 1 天、前端 0.5 天。
