## 3. 验证 3：运行时冒烟（真实 MySQL8 + Redis7）

### 3.1 ✅（已修复并复验）单位换算"当前生效版本"查询跨时区恒空 — commit `f91fe71`

- **现象**：连续写入两条换算（v1 rate12、v2 rate10）后，
  `GET /api/v1/catalog/unit-conversions/current?skuId=...&fromUnit=QA_U1`
  → `HTTP 200 {"code":0,"message":"成功"}`，**`data` 字段缺失（即 null）**。
- **期望**：返回最大 `version`（=2，rate 10）且 `effective_from <= now` 的记录（设计 §2.2.1、R-X-02）。
- **根因（已用 DB 证据锁定）**：
  - 应用写入 `effective_from` 用 **JVM 本地时间（Asia/Shanghai）** → 落库 `2026-09-22 12:42:50`。
  - Mapper 用 **DB 的 `NOW()`** 比较；容器 MySQL 运行在 **UTC** → `NOW()=04:42:50`。
  - `effective_from <= NOW()` → `12:42:50 <= 04:42:50` = **false** → 无行 → 返回 null。
  - 反证：把比较值改为显式 `'2026-09-22 23:59:59'` 后，SQL 立即返回 v2 行；`SELECT NOW()` 实测 UTC。
- **定位**：`backend/src/main/java/com/dzgylxt/mapper/catalog/UnitConversionMapper.java:18`
  `... AND (effective_from IS NULL OR effective_from <= NOW())`
- **影响**：R-X-02「单位换算快照」跨模块契约（P2 下单取快照）依赖此接口，当前不可用。
- **修复建议**：由 Java 传入基准时间比较（如 `effective_from <= #{now}` 传 `LocalDateTime.now()`），或统一 DB/应用时区；避免"应用写本地时间、DB 用自身 `NOW()`"这类跨时区比较。
- **备注**：本缺陷在 `docker-compose.yml`（MySQL `TZ: Asia/Shanghai`）下不显现，仅在 DB 时区 ≠ 应用时区时暴露；建议仍按上述加固。
- **修复（commit `f91fe71`，本地 develop）**：`selectCurrentEffective` 增加 `@Param("now") LocalDateTime`，SQL 改为 `effective_from <= #{now}`；`UnitConversionServiceImpl.currentEffective` 传入 `LocalDateTime.now()`（与写入同源应用时钟）。
- **第 2 轮复验证据（UTC 容器下）**：
  - `GET .../unit-conversions/current?skuId=…&fromUnit=QA_U1` → **`data` 返回 v2（rate=10，effectiveFrom=2026-09-22T13:15:02）** ✔
  - 语义保持：再写入一条 **未来生效** v3（rate=99，effectiveFrom=次日）后，current **仍返回 v2**（未来版本被 `<= now` 正确排除）✔
  - 全仓 grep 确认无其它 `NOW()`/`CURRENT_TIMESTAMP` 实时 SQL（仅剩 1 处 Javadoc 文字）✔
