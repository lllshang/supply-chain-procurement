## 2. 用例组 A：G2 合同经办信息

### UC-G2-01 新建合同并填写经办信息

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 进入「合同管理」（合同登记页） | 显示合同列表，列表含「经办人」「签订日期」两列 |
| 2 | 点击右上角 **合同登记** 按钮（需 `contract:write` 权限，admin 具备） | 弹出合同登记表单 |
| 3 | 填写表单必填项：供应商、关联中标、合同标题、合同类型、金额等 | 正常填写 |
| 4 | 在新增的 4 个字段填写：<br>• **经办部门**<br>• **经办人**<br>• **签订日期**（日期选择器，格式 YYYY-MM-DD）<br>• **关联项目(选填)**（填项目 ID，可留空） | 4 个字段均可输入 |
| 5 | 点击 **保存** | 提示保存成功，列表新增一行 |

**核对点：**
- 列表「经办人」列显示步骤 4 填写的经办人；「签订日期」列显示日期。
- （DB 核对，可选）执行：
  ```sql
  SELECT owner, owner_dept, sign_date, project_id
  FROM contract
  ORDER BY id DESC LIMIT 1;
  ```
  应与填写值一致（`project_id` 未填则为 NULL）。

### UC-G2-02 编辑草稿合同补充经办信息

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 在合同列表中找到状态为「草稿」的合同，点击其 **编辑** 按钮 | 打开编辑表单 |
| 2 | 补充/修改经办部门、经办人、签订日期、关联项目 | 正常输入 |
| 3 | 点击 **保存** | 提示保存成功 |

**核对点：** 列表「经办人」「签订日期」列随编辑更新；DB 中 `owner/sign_date` 等字段同步更新（仅草稿合同可编辑，非草稿会报「仅草稿合同可编辑」）。

### UC-G2-03 经办信息展示核对

- 列表已常驻「经办人」「签订日期」两列，无需额外操作即可核对新建/编辑结果。
- 若合同详情页也展示经办信息，进入详情核对一致性（以列表列为准即可满足验收）。

## 3. 用例组 B：G4 付款冲销 / 作废

> 后端端点：`POST /api/v1/payments/{id}/void`，body `{ "reason": "..." }`
> 规则（复刻 B9 Settlement VOIDED 范式）：`UNPAID`/`PAID` → `VOIDED(已作废)`；原因必填；已作废不可重复；无预算动作（仅改状态 + 记录原因/操作人/时间）。

### UC-G4-01 对「未付(UNPAID)」付款单作废

**前置：** 付款登记列表中存在状态为「未付」的付款单。若没有，先点 **新建付款单** 创建一条（或挑一条可作废的单）。

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 进入「付款登记」页 | 显示付款单列表，状态列由 `StatusTag` 渲染 |
| 2 | 在状态为「未付」的行，操作列出现红色 **作废/冲销** 按钮 | 按钮仅对 `UNPAID`/`PAID` 显示 |
| 3 | 点击 **作废/冲销** | 弹窗「请填写作废/冲销原因」输入框 |
| 4 | 输入原因（如「重复付款，予以作废」），点确定 | 提示「已作废/冲销付款单」，该行状态变为 **已作废** |
| 5 | 观察该行操作列 | 「作废/冲销」按钮消失（已作废不可再作废） |

**核对点（DB）：**
```sql
SELECT status, voided_reason, voided_by, voided_at
FROM payment WHERE id = <该付款单ID>;
```
- `status = 3`（VOIDED）
- `voided_reason` = 输入的原因
- `voided_by` = 当前操作人 ID（admin=1）
- `voided_at` = 作废时间（非空）

### UC-G4-02 对「已付(PAID)」付款单冲销

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 找状态为「已付」的付款单，点 **作废/冲销** | 弹窗输入原因 |
| 2 | 填原因并确定 | 状态变为「已作废」，按钮消失 |

**核对点：** 同 UC-G4-01 的 DB 核对；冲销后该单不再参与对账口径（见 UC-G4-05）。

### UC-G4-03 重复作废应被拒绝

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 对一条「已作废」付款单再次尝试作废 | 操作列已无按钮；若直接调接口，返回 `STATUS_INVALID`：`付款单已作废，请勿重复操作` |

### UC-G4-04 原因必填校验

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 点作废，原因**留空**直接确定 | 前端提示「原因必填」并拦截；若绕过前端直接调接口（空 reason），后端返回 `PARAM_ERROR：作废/冲销原因必填` |

### UC-G4-05 对账单口径排除已作废（可选）

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 点「供应商对账单」，输入供应商 ID 查询 | 对账单金额/明细**不含**已作废(VOIDED)付款单 |

## 4. 异常 / 边界（已自动验证，供参考）

| 场景 | 预期 |
|---|---|
| 未登录直接调 `POST /api/v1/payments/{id}/void` | HTTP **401**（GUARD 鉴权拦截） |
| 作废不存在的付款单（正确 token） | 结构化错误 `DATA_NOT_FOUND：付款单不存在：<id>` |
| 原因缺失（正确 token + 存在 id） | `PARAM_ERROR：作废/冲销原因必填` |
