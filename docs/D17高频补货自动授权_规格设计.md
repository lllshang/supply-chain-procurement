# D17 高频补货自动通过授权 · 规格设计

> 来源：主流程 docx《顶点公园供应链采购三链路与订单关系说明》"日常采购控制口径"末段
> 定位：D14 日常采购「授权」控制的**增强开关**；D14 已落地授权留痕 + 超额度升级（DAILY_AUTH 人工确认），本项在业务开启时把"人工升级确认"简化为"系统自动通过"。
> 状态：⏳ 待实现（P4 已预留配置键名 `app.order.daily-auto-auth-enabled`，逻辑 P4 之后）

## 1. 背景与依据

主流程 docx 明确：

> 普通高频补货且价格、数量固定时，可按配置自动通过授权校验并从有效合同直接生成订单。
> **该自动通过只简化内部审批，不代表跳过合同关联、预算校验或授权留痕。**

即：高频补货场景允许业务"免人工确认"直接下单，但**合同关联、预算校验、授权留痕三件事一件都不能少**——
这三点已由既有实现（合同额度闸 / 预算占用 / D14 `authorized_by·name·time`）保证，本项只动"是否生成 DAILY_AUTH 升级审批任务"这唯一的内部审批环节。

## 2. 范围

| 项 | 是否纳入 D17 |
|---|---|
| 配置开关开启时，日常采购订单（applyId==null）跳过 DAILY_AUTH 人工升级任务 | ✅ |
| 跳过升级任务的同时，**仍记录授权留痕**（authorized_by/name/time 非空） | ✅（审计必须可追溯"系统自动授权"） |
| 新增 `auto_authorized` 列标记"系统自动授权通过"（与 `auth_over_limit` 区分） | ✅ |
| 合同关联 / 预算校验 / 授权确认（创建人须为已授权内部用户） | ❌ 不改动（D14 已保证，本项不触碰） |
| 标准/项目链路订单（有 applyId） | ❌ 不在范围内（走审批流已覆盖授权） |
| SKU 级"高频补货"白名单 | ⏭️ 本期不做（开关即业务口径；如需按物料精细控制，预留后续扩展） |

## 3. 配置项（application.yml `app.order`）

```yaml
app:
  order:
    daily-auth-enabled: true          # D14 开关（保持）
    daily-auth-limit: 500000          # D14 占位阈值（待拍板）
    # D17 高频补货自动通过授权开关（默认关；开启后日常采购跳过 DAILY_AUTH 人工升级，仍保留授权留痕）
    daily-auto-auth-enabled: false
```

读取方式：复用 D14 的 `@Value("${app.order.daily-auto-auth-enabled:false}")` 模式（默认关，业务显式开启才生效）。

## 4. 数据模型（purchase_order 表新增 1 列）

| 列名 | 类型 | 含义 |
|---|---|---|
| `auto_authorized` | TINYINT NULL DEFAULT 0 | 是否由系统自动授权通过（0 否 / 1 是）。D17 开启且日常采购订单时置 1，区别于 `auth_over_limit`（超额度人工升级）。审计可区分"人工确认"与"系统自动通过"。 |

> 与 `auth_over_limit` 正交：二者不会同时为 1。`auto_authorized=1` 表示本次授权未经人工确认（系统按配置自动通过）；`auth_over_limit=1` 表示超阈值待人工确认（DAILY_AUTH 任务在途）。

## 5. 逻辑（OrderServiceImpl.createOrder，仅 `applyId == null` 分支）

在 D14 既有逻辑之后微调（不改动合同闸/预算闸/授权确认闸门）：

1. 授权确认（硬控制，创建人须持有系统权限）——**不变**。
2. 授权留痕（authorized_by/name/time）——**不变**。
3. **D17 自动授权标记**：`autoAuthorized = dailyAutoAuthEnabled`（开关开启且为日常采购即置位）。
4. 超单笔授权额度升级判定改为：
   - 原：`totalAmount > dailyAuthLimit` → `authOverLimit = true` → 生成 DAILY_AUTH 任务。
   - 新：`totalAmount > dailyAuthLimit && !dailyAutoAuthEnabled` → `authOverLimit = true`（生成任务）；
     若 `dailyAutoAuthEnabled` 为真，则**不置 `authOverLimit`、不生成 DAILY_AUTH 任务**，由 `autoAuthorized=1` 标记系统自动通过。
5. `insertOrder` 透传 `autoAuthorized`，落 `auto_authorized` 列。

> 契约不变：D14 的 `authorized_by/name/time` 始终写入（留痕不跳过）；`createDailyAuthTask` 仅在 `authOverLimit=true` 时触发。
> 默认 `daily-auto-auth-enabled=false`，现网行为与 D14 完全一致（零回归风险）。

## 6. 验收标准（AC）

| # | AC | 验证方式 |
|---|---|---|
| AC1 | 开关关闭（默认）：日常采购超额度订单仍生成 DAILY_AUTH 任务，`auth_over_limit=1`，`auto_authorized` 为空/0 | 单测（mirror D14）：断言 `approvalGateway.create` 调用 1 次 bizType=DAILY_AUTH |
| AC2 | 开关开启：日常采购超额度订单**不生成** DAILY_AUTH 任务，`auto_authorized=1`，`authorized_by/name/time` 仍非空 | 单测：`approvalGateway.create` 未被调用；断言 `auto_authorized=1` 且三留痕字段非空 |
| AC3 | 开关开启、授权确认闸门仍生效：创建人无权限仍抛"无日常采购授权" | 单测：`perms=[]` 抛异常（与 D14 一致） |
| AC4 | 开关开启不跳过合同/预算闸：超合同可用额度仍被拒 | 单测：合同闸抛"超出合同可用额度" |
| AC5 | DDL 兼容：新建库（schema.sql）含 `auto_authorized` 列 | 建库或人工核对 DDL |

## 7. 风险 / 待确认

- **R1**：开关默认关，业务须显式开启才生效；开启即表示接受"高频补货订单不经人工确认直接下单"，仅适用于价格/数量固定的常规补货。
- **R2**：`auto_authorized` 与 `auth_over_limit` 互斥，报表/审计按两列分别呈现即可区分授权来源。
- **R3**：P4 真实审批上线后，DAILY_AUTH 任务转为拦截式"部门负责人/采购负责人确认"；D17 开启时该人工确认被系统自动通过替代，符合 docx"只简化内部审批"口径。
