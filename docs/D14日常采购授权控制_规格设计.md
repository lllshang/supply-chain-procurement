# D14 日常采购「授权」控制 · 规格设计

> 来源：主流程 docx《顶点公园供应链采购三链路与订单关系说明》（rev 137）
> 定位：P3c 之后、P4（审批单据中心）之前的**硬控制补缺**；与 P4 审批能力天然衔接。
> 状态：⏳ 待实现（已出规格，编码中）

## 1. 背景与依据

主流程 docx 明确：日常采购（基于有效框架/年度合同、无采购申请来源）**可以免采购审批**，但
**合同、预算和授权三项控制不能省略**：

> - 必须选择有效合同/框架合同（✅ 已实现：合同 EFFECTIVE + 有效期 + 额度闸）
> - 必须完成预算校验和占用（✅ 已实现：预算占用/释放/核销）
> - **必须记录授权人和授权时间**
> - 预算充足不等于不需要任何人操作，**系统仍需确认订单创建人具备授权**，并在订单生成时形成预算占用
> - （控制规则表）合同范围内，但**金额超过单笔授权额度 → 部门负责人或采购负责人确认**

此前 PRD 未强调"授权"子项，实现中**完全缺失**（grep `授权人/授权时间/授权额度/authoriz*` 代码零命中）。
本次补齐。

## 2. 范围

| 项 | 是否纳入 D14 |
|---|---|
| 日常采购订单（下单入口 `applyId == null`）的授权校验 + 留痕 | ✅ |
| 超单笔授权额度 → 部门负责人/采购负责人确认（升级审批） | ✅（复用现有 `ApprovalGateway`，目前 `LocalApprovalGateway` 即审即过，P4 落地后转真实审批） |
| 标准/项目链路订单（有 `applyId`）的授权 | ❌（审批流已覆盖授权，本项仅针对免审批的日常采购） |
| 高频补货自动通过授权的配置开关 | ⏭️ 拆为 **D17**（依赖本项字段与阈值） |
| 变更单（changeOrder）超额度再升级 | ⏭️ 本期不做，留待 P4 统一审批时一并覆盖（见 §6 风险） |

## 3. 数据模型（purchase_order 表新增 4 列）

| 列名 | 类型 | 含义 |
|---|---|---|
| `authorized_by` | BIGINT NULL | 授权人用户 ID（日常采购=订单创建人） |
| `authorized_name` | VARCHAR(50) NULL | 授权人姓名/账号（冗余便于审计，不等登录态失效后丢失） |
| `authorized_time` | DATETIME NULL | 授权时间（= 订单生成时间） |
| `auth_over_limit` | TINYINT NULL DEFAULT 0 | 是否超单笔授权额度升级（0 否 / 1 是） |

> 与 `BaseEntity.created_by`（创建人，自动填充）区分：授权人语义上在日常采购场景等于创建人，
> 但字段独立，便于将来授权可委托/代理时分离，也便于审计报表单独呈现"授权"维度。

## 4. 配置项（application.yml `app.order`）

```yaml
app:
  order:
    # D14 日常采购授权控制开关（默认开启）
    daily-auth-enabled: true
    # D14 单笔授权额度阈值（元）。超过则升级至部门负责人/采购负责人确认。
    # ⚠️ 占位值，待业务拍板（对应主流程 docx 控制规则表"单笔授权额度"，docx 未给具体数值）
    daily-auth-limit: 500000
```

读取方式：复用 `ContractServiceImpl` 的 `@Value("${app.contract.approve-threshold:500000}")` 模式。

## 5. 逻辑（OrderServiceImpl.createOrder，仅 `applyId == null` 分支）

在现有"校验②合同额度闸"之后、落单（insertOrder）之前插入：

1. **取当前用户**：`LoginUser u = UserContext.get()`。
2. **授权确认（硬控制，仅在生产安全上下文下强制）**：
   - 若 `dailyAuthEnabled && u != null && u.getPerms() 为空` → 抛 `BizException("无日常采购授权：当前用户未持有任何系统权限")`。
   - 若 `u == null`（仅单测/内部无安全上下文调用）：放行但授权人记空，便于审计追踪（不阻断测试基线）。
   - 说明：因全局 `@PreAuthorize` 已要求"已登录且至少一权限"，生产环境 `u` 必非空且必有 perms，
     故本闸门等价于"确认订单创建人为已授权的内部用户（非供应商 H5 / 非匿名）"。
3. **授权留痕**：`authorized_by = u.getId()`、`authorized_name = u.getUsername()`、`authorized_time = now`。
4. **超额度升级**：
   - 若 `totalAmount > dailyAuthLimit`：`auth_over_limit = 1`，并调用 `createDailyAuthTask(order, totalAmount)`
     （复用 `#47` 的 `ApprovalGateway` + `REQUIRES_NEW` 事务模板，`bizType="DAILY_AUTH"`，标题
     `"日常采购超授权额度确认-订单{orderNo}"`）。
   - 订单仍落 `OrderStatus.CREATED`（预算已占用），升级任务供审计/待办；当前 `LocalApprovalGateway`
     即审即过，P4 落地后转为真实"部门负责人/采购负责人确认"。

> `createDailyAuthTask` 结构镜像现有 `createBudgetUpgradeTask`（L738）：`approvalGateway == null` 时跳过；
> payload 含 `orderId / orderNo / totalAmount / limit / deptId`，`bizId = order.getId()`。

## 6. 验收标准（AC）

| # | AC | 验证方式 |
|---|---|---|
| AC1 | 日常采购订单生成后 `authorized_by / authorized_name / authorized_time` 非空且等于当前登录用户 | 单测：注入 SecurityContext（含 user）后建单，断言三字段 |
| AC2 | 无安全上下文（单测默认）不抛异常，授权人字段允许为空（兼容现有 133 测试基线） | 现有 `OrderTripleCheckTest` 全量仍绿 |
| AC3 | 当前用户无任何系统权限时，日常采购建单抛"无日常采购授权" | 单测：注入 perms=[] 的 user，断言抛异常 |
| AC4 | 金额 ≤ 阈值：不生成 DAILY_AUTH 任务，`auth_over_limit=0` | 单测断言 `approvalGateway.create` 未被调用 |
| AC5 | 金额 > 阈值：生成 DAILY_AUTH 任务且 `auth_over_limit=1` | 单测（mock `approvalGateway`）断言调用 1 次且 bizType=DAILY_AUTH |
| AC6 | DDL 兼容：新建库（db/schema.sql）与存量库（d14_schema.sql 幂等迁移）均含 4 列 | 集成测试建库 + 手工 `mysql ... < d14_schema.sql` 可重复执行 |

## 7. 风险 / 待确认

- **R1（待业务拍板）**：`daily-auth-limit` 默认 50 万为占位值（与合同 50 万阈值同口径），docx 未给具体数值。
- **R2（待业务拍板）**："授权人"是否可能 ≠ "创建人"（委托/代理授权）？当前取创建人，字段已独立预留。
- **R3（范围边界）**：变更单（changeOrder）超额度再升级本期未做，依赖 P4 统一审批框架，已在 §2 标注。
- **R4**：`auth_over_limit` 升级任务在当前 `LocalApprovalGateway` 下即审即过，订单不会卡在待审；
  这是预期过渡态，P4 真实审批上线后即生效拦截。
